攻撃・脆弱性に関する言葉

PHP2Shell / CVE-2026-109618・CVE-2026-109619
この教材が題材にする PHP-FPM のリクエスト解析処理のメモリ破壊脆弱性の総称と、その CVE 番号。 細工したリクエストでワーカーを異常終了させられ、条件が揃えば RCE につながりうる。 対策はバージョン更新(8.4.26→8.4.27)。
CVE
Common Vulnerabilities and Exposures。公開された脆弱性に付けられる世界共通の識別番号。 「ソフト本体のバグ」なので、原則バージョン更新(パッチ)で直す。
RCE(リモートコード実行 / リモートシェル実行)
Remote Code Execution。攻撃者が送り込んだコマンドやコードを、遠隔からサーバー上で実行させてしまうこと。 成功すると「シェルを取られる」=サーバーを乗っ取られる。PHP 固有ではなく、あらゆる言語・環境で起こりうる。
メモリ破壊 / バッファオーバーフロー / Use-After-Free
プログラムが想定外の場所のメモリを書き換えてしまう不具合。 用意されたバッファ(入れ物)を超えて書き込む(オーバーフロー)、 解放済みの領域を使い続ける(Use-After-Free)などがあり、クラッシュや RCE の原因になる。
ヒープ / スタック
プログラムが使うメモリの領域。ヒープは実行中に必要なだけ確保・解放する自由な領域、 スタックは関数呼び出しのたびに積み下ろしする領域。 バッファオーバーフローや Use-After-Free は、これらの領域で起きる。 どこがどう壊れるかで、クラッシュで済むか悪用されるかが変わる。
メモリリーク
確保したメモリを解放し忘れ、使い終わった領域が少しずつ溜まっていく不具合。 長く動かすほどメモリ使用量が増え、やがて枯渇して動作が不安定になる。 攻撃者が意図的に誘発できると、可用性を落とす DoS の糸口になりうる。
OOM(メモリ枯渇 / Out Of Memory)
使えるメモリを使い切った状態。PHP では Allowed memory size exhausted のようなエラーで止まり、 プロセスが異常終了することもある。OS 全体で枯渇すると、OS が OOM Killer でプロセスを強制終了する。 今回の検証でワーカーが異常終了したのも、過大な入力でメモリを使い切らせたことが一因。 可用性(サービスを使い続けられること)を脅かす。
DoS(サービス妨害)
Denial of Service。サーバーを異常終了・過負荷にさせ、正規利用者がサービスを使えなくする攻撃。 この教材ではワーカーの異常終了を繰り返させられる状態が DoS の入口になると説明している。
PoC(概念実証) / 攻撃スクリプト
Proof of Concept。脆弱性が本当に存在することを示す検証用コード。 公開されていても、環境条件が噛み合わなければ「実行するだけで必ず攻撃成功」とはならない。
Web シェル
攻撃者がサーバーに置く、Web 経由でコマンドを実行できる不正なスクリプト。 アップロードされた .php が実行できてしまうと設置されやすい。

サーバー・設定に関する言葉

DocumentRoot / 公開領域・非公開領域
DocumentRoot は Web サーバーが外部に公開するディレクトリ。 この教材では public/ だけを公開領域にし、ソースや .env は外(非公開領域)に置くのが対策。
.env
DB パスワードや API キーなど環境ごとの秘密情報を書く設定ファイル。 公開領域に置くと HTTP で直接取得され情報漏洩する。これは設定・配置の問題で、PHP の脆弱性ではない。 ※ Web サーバー(Nginx の try_files/location など)で返す設定自体が危険なのではなく、 機密ファイルが公開領域内に置かれ遮断されていないことが問題。原則は公開領域の外に置く。
multipart POST(multipart/form-data)
ファイル添付などに使われるフォーム送信形式。この形式の解析処理に今回の脆弱性があり、 細工した multipart POST でワーカーを異常終了させられた。
パストラバーサル(ディレクトリトラバーサル)
../ などを使って、公開を許していないディレクトリの外のファイル (例: /etc/passwd)へアクセスする攻撃。 「公開領域の外へ抜け出す」問題で、公開領域内の機密ファイルを返してしまう .env 漏洩とは別物。 ユーザー入力をそのままファイルパスに使う実装(例: PHP の include($_GET['page']))や、 Web サーバーのパス設定ミスが原因になる。 ※ Nginx は照合前に URI を正規化して ../ を畳むため、素朴な ../ だけでは外へ出られない。 トラバーサルが成立するのは alias の末尾スラッシュ漏れ(off-by-slash)など別の設定ミスと組み合わさったとき。
OS コマンドインジェクション(シェル実行)
攻撃者の入力がそのまま OS のコマンドとして実行され、サーバー上で任意のコマンド(シェル)を動かされてしまう攻撃。 言語を問わず起こる代表的な脆弱性で、入力をコマンドに組み立てる処理が原因。 ※ PHP では exec() / system() / shell_exec() などが該当し、 php.ini の disable_functions で無効化するのは補助的な防御。根本は入力を信用しない設計。
許可リスト(allowlist) / エスケープ
インジェクション対策の基本となる2つの考え方。 許可リストは「あらかじめ決めた安全な値だけを受け付け、それ以外は拒否する」方式(逆に危険な値を列挙して弾く拒否リストは漏れやすい)。 エスケープは、入力をコマンドやクエリに渡す前に特別な意味を持つ文字を無害化すること。 共通の原則は「外部入力をそのまま実行対象に使わない」。 ※ 教材の exec-demo.php は、OS コマンド実行と非公開領域の参照を実演しつつ、 許可リストと escapeshellarg()(エスケープ)で安全に作ってある例。 入力を直接 exec() に渡していれば、そこで初めてコマンドインジェクション(RCE)が成立する。 そもそもこうした .php を公開領域に置かないのが本来の対策。
ファイルインクルード(LFI / RFI)
プログラムが外部から指定されたファイルを読み込んで実行してしまう脆弱性。 サーバー内のファイルを読む LFI(ローカルファイルインクルード)、 外部 URL のコードを読む RFI(リモートファイルインクルード)に分かれる。 ユーザー入力をそのまま読み込み先に使う実装が原因で、言語を問わず起こる。 ※ PHP では include / require が該当し、 php.ini の allow_url_include を Off にすると RFI を防げる。
セッション / Cookie / PHPSESSID
セッションは、サーバーが利用者ごとの状態(ログイン状態など)を覚える仕組み。 サーバー側にデータを保存し、その識別子(セッション ID)をブラウザに Cookie として渡す。 PHP ではこの Cookie 名が既定で PHPSESSID。 以降ブラウザは毎回この Cookie を送り、サーバーは ID をキーに保存データを取り出す。 主なセキュリティ上の注意
  • ・セッションハイジャック(乗っ取り)：セッション ID を盗まれると、その利用者になりすまされる。
  • ・セッションフィクセーション(固定化)：攻撃者が用意した ID を使わせ、ログイン後に乗っ取る。ログイン時に ID を再発行して防ぐ。
  • ・Cookie の属性：HttpOnly(JS から読めなくし XSS での盗難を防ぐ)、 Secure(HTTPS でのみ送信)、SameSite(別サイトからの送信を制限し CSRF を軽減)を付ける。
  • ・不要な書き込み経路を残さない：リクエストを受け取るだけでセッションにデータが作られる機能は、使わないなら止める。
phpinfo() / info.php
PHP の設定情報を一覧表示する関数とその実習用ファイル。情報が多く攻撃の手がかりになるため、 確認後は削除する。公開領域に残すのは危険。

運用・基盤・ツールに関する言葉

Linux
Web サーバーの土台としてよく使われる OS(基本ソフト)。Nginx や PHP-FPM はこの上で動く。 ファイルの所有者・権限(誰が読み書き・実行できるか)の仕組みがあり、 公開ファイルやアップロード先の権限を適切に絞ることがセキュリティの基本になる。
Web サーバー / FastCGI
Web サーバーはブラウザからの HTTP リクエストを受け取り、ファイルを返したりプログラムの実行を仲介したりするソフト(Nginx・Apache など)。 FastCGI は Web サーバーと PHP などのプログラム実行役(PHP-FPM)をつなぐ取り決め。 Nginx が .php を受けると、FastCGI 経由で PHP-FPM に処理を渡す。
Nginx
軽量で高速な Web サーバー。リクエストの振り分け(どの URL をどう処理するか)を設定で細かく決める。 PHP は自分で実行せず、FastCGI で PHP-FPM に渡す構成が一般的。
Apache
歴史の長い代表的な Web サーバー。PHP を内部のモジュールとして自分で実行できる構成が使え、 ディレクトリごとに .htaccess で設定を上書きできるのが特徴。 Nginx が「中央の設定ファイルでまとめて制御」なのに対し、Apache は「各所で柔軟に上書き」できる点が対照的。
PHP-FPM
PHP を実行する常駐プロセス(FastCGI Process Manager)。Web サーバーから .php の処理を受け取り、 複数のワーカーで並行処理する。今回の CVE はこの解析処理にあった。
Docker / Docker Compose
アプリと実行環境をコンテナとしてまとめ、同じ状態を再現する仕組み。 Compose は複数コンテナ(Nginx・PHP-FPM など)をまとめて起動する。
Composer
PHP の依存ライブラリ管理ツール。composer install で vendor/ を生成する。
パッチ適用 / バージョン更新
脆弱性が修正された新しいバージョンに上げること。CVE 由来の問題は、設定変更ではなくこれでしか根本的に塞げない。
